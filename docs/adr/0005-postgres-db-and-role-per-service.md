# ADR-0005: One PostgreSQL instance, one database and role per service

- **Status:** Accepted
- **Date:** 2026-07-28
- **Milestone:** M0 (decision), M4 (implementation)

## Context

Several services need PostgreSQL: n8n, Paperclip, Hermes, and future agents.
Two obvious extremes: one shared database for everything, or one Postgres
container per service.

A shared database with a shared superuser means any service can read and modify
any other service's data, and a single credential leak exposes everything.
One container per service triples RAM usage on a 3.7 GB host and multiplies
backup and upgrade work.

## Decision

**One PostgreSQL server. Per service: its own database, its own role, no rights
to any other database.**

```
postgres (one container, one major version)
├── n8n        owner: n8n_user
├── paperclip  owner: paperclip_user
└── hermes     owner: hermes_user
```

- The superuser is used only for bootstrapping roles. No application uses it.
- Each role has `CONNECT` on its own database only; `PUBLIC` connect rights are
  revoked from every application database.
- Each service's password is a separate entry in `.env`.

**Explicit exception path:** if a service later requires a different Postgres
major version, it gets its own container. The Compose structure supports this
without restructuring — it is a new service block, not a redesign.

## Alternatives considered

**One database, one shared user.** Simplest. Rejected: no isolation of data or
credentials; one leaked password exposes everything.

**One database, separate schemas.** Lighter than separate databases. Rejected:
schema-level permissions in Postgres are subtle and easy to get wrong;
`search_path` mistakes silently cross boundaries. Databases are the clearer
boundary.

**One container per service.** Full isolation, independent versions. Rejected
as the default: ~250 MB RAM each on a 3.7 GB host, and every backup and upgrade
procedure multiplies. Retained as the documented exception.

## Trade-offs

**Gained:** credential and data isolation at the cost of one instance's memory.
A compromised n8n cannot read Hermes' tables. Backups are one consistent dump.

**Given up:** all services share a major-version upgrade event and must be
coordinated. A runaway connection leak in one service can exhaust
`max_connections` for all — mitigated by per-role connection limits in M4.

**Correlated failure accepted:** the Postgres container going down takes every
service with it. On a single host this is largely unavoidable; the alternative
trades it for three times the operational surface.

## Consequences

- M4 provisions roles via an init script, not by hand, so it is reproducible.
- `.env` holds `POSTGRES_<SERVICE>_PASSWORD` per service, generated by
  `scripts/setup-env.sh`.
- Adding a database-backed service means adding a role, a database and a
  password — this must be scripted, not manual.
- Per-role `CONNECTION LIMIT` is set so one service cannot starve the others.
