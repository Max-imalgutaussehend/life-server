Both databases sit on `net-data` only — `internal: true`, no published port.
Nothing outside that network can reach them, and they have no route out.

## Why these choices

**`maxmemory-policy noeviction` on Redis.** The tempting default,
`allkeys-lru`, would silently evict n8n queue jobs under memory pressure —
losing work with no error anywhere. `noeviction` makes writes fail loudly
instead. A lost job that reports itself beats a lost job that doesn't.

**`work_mem = 8MB`, deliberately small.** The real memory ceiling is
`work_mem` × concurrent sort/hash operations, not `work_mem`. On a host shared
with Caddy, cloudflared and later application containers, a generous `work_mem`
is the standard way a Postgres box gets its containers OOM-killed.

**`wal_level = replica`.** Keeps physical backups and point-in-time recovery
possible for M5. `minimal` is marginally faster and forecloses both.

**Passwords injected, never committed.** `redis.conf` is in Git, so
`requirepass` comes from `.env` via the container's shell at startup (ADR-0006).

**The init script is registry-driven.** `POSTGRES_SERVICES` comes from the
compose file rather than the script restating the service list (ADR-0014), and
a service missing its password is reported as `WARN`, not skipped silently.

## The password leak, and the fix

`postgresql.conf` sets `log_statement = 'ddl'` so schema changes are never a
mystery after the fact. **`CREATE ROLE ... PASSWORD` is DDL.** The first
provisioning run therefore wrote all three service passwords in plaintext into
the container log:

```
LOG:  statement: CREATE ROLE n8n LOGIN PASSWORD 'bn7DNDrh…' CONNECTION LIMIT 20
```

Three plaintext passwords, readable via `docker logs` and in
`/var/lib/docker/containers/<id>/<id>-json.log`.

Fixed in three parts:

1. The init script now opens each provisioning session with
   `SET log_statement = 'none'` — **session-scoped**, so the global DDL-logging
   policy is untouched. Weakening `log_statement` would have been the wrong fix.
2. The three passwords were rotated in `.env`, and the container plus its volume
   were destroyed and rebuilt — which discards the log file with them. The
   databases held zero user tables at that point, verified before deleting, so
   nothing was lost.
3. `postgresql.conf` carries a `HAZARD:` note at the `log_statement` line, and
   `verify-data-layer.sh` asserts no password appears in the log — so a
   regression fails a test rather than going unnoticed.

Worth internalising: **a safe-sounding audit setting became a credential
disclosure** because of one overlap between "DDL" and "statements containing
secrets". The setting was right; its blast radius was not thought through.

## Operating notes

```bash
make verify-data          # re-run every assertion above
make psql                 # superuser shell, maintenance database
make psql DB=n8n          # a service database
```

**Adding a database-backed service later** — do not destroy the volume. Add the
password to `env.example` and `.env`, add the name to `POSTGRES_SERVICES` in the
compose file, then re-run the init script by hand:

```bash
docker compose exec postgres \
  /docker-entrypoint-initdb.d/10-roles-and-databases.sh
```

It is idempotent: existing roles get `ALTER ROLE`, existing databases are left
alone.

## Known limitations

**Redis has no per-service access control.** `SELECT n` is logical separation,
not security — any service with the password can read every database. Isolation
here rests entirely on `net-data` membership. Anything that genuinely must be
unreadable by another service belongs in Postgres. Database assignments are
recorded in `redis.conf` so two services cannot silently claim the same number.

**A shared instance means a shared failure and a shared upgrade.** Accepted in
ADR-0005; the per-role connection limits are what stop one leaking service from
starving the others.

## Rollback

```bash
ssh -i ~/.ssh/life-server deploy@62.238.4.64 'cd /opt/life-server && \
  docker compose -f compose/docker-compose.prod.yml rm -sf postgres redis'
```

Volumes survive; add `-v` to destroy the data too. Caddy, cloudflared and
whoami are unaffected — nothing in M1–M3 depends on the data layer.

## Next: M5 before M6

ADR-0009 requires backups to ship before the first stateful service. Postgres
and Redis now exist but hold **no application data**, so nothing is at risk
today. That changes the moment n8n (M6) writes its first workflow.

**M5 must land before M6**, and its restore must be rehearsed, not assumed —
`RESTIC_REPOSITORY` in `.env` is still `__SET_MANUALLY__`, which is the first
thing M5 needs.
