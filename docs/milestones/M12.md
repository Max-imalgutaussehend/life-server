## Why the generator needed a new field

Every hostname in this repo derives from `<name><ENV_PREFIX>.<DOMAIN>`. A bare
domain has no label to put the service name into, so the rule simply could not
express it. The options were a hand-written exception in the generated
Caddyfile — which `make check` would then fight with on every run — or teaching
the registry the concept. ADR-0014 makes that choice for us: fix the generator,
not the output.

`apex: true` is validated like everything else, and **only one enabled service
may claim it**. Two would render two Caddy site blocks for the same address and
Caddy would refuse to start; the generator now rejects that with a message
naming the current owner.

### The one place that is not env-prefixed

The apex block cannot carry `.dev`, because there is no label to put it in.
Prod and dev would therefore both claim `{$DOMAIN}` and the second stack to
start would fail to bind. **Only one environment may run an apex service.**
Today that is prod; a dev apex would need a genuinely different domain, which
is a registry change rather than a template tweak.

## Why a public endpoint is acceptable here

M11 removed `whoami` partly because it was the only unauthenticated endpoint on
a host that runs agents. Re-adding a public service deserves the same scrutiny:

- It serves **files**. No request echo, no application logic, no input to parse,
  no session, no database.
- `networks: [apps]` only — no route to Postgres, Redis or the agent network.
  There is nothing to steal from it and nowhere to pivot to.
- `read_only: true` with tmpfs for Caddy's scratch dirs: a write primitive has
  nowhere to persist.
- The site is mounted `:ro`, so the container cannot alter what it serves.
- CSP `default-src 'none'`, `frame-ancestors 'none'`, nosniff — the page has no
  scripts at all, so the strictest policy costs nothing.

**Do not put anything dynamic behind this hostname without a new ADR.** The
value of "the one public endpoint only serves static files" is that the
sentence stays true.

## What only you can do

`https://maxrommel.de` returns **522** (Cloudflare cannot reach the origin), and
the internal path is proven to work. The cause is the one documented in M8.5:

**The tunnel runs token-managed**, so it takes ingress from the Cloudflare
dashboard and never reads `compose/generated/cloudflared/config.yml`. That file
is the reviewable record of intent, not a live config — editing it changes
nothing at runtime.

`.env` holds only `CLOUDFLARE_TUNNEL_TOKEN`, which authenticates the tunnel but
cannot create routes, so this cannot be automated from here.

### The fix (~2 minutes)

Cloudflare Zero Trust → **Networks** → **Tunnels** → your tunnel → **Published
application routes** → *Add a published application route*, twice:

| Subdomain | Domain | Type | URL |
|---|---|---|---|
| *(leave empty)* | `maxrommel.de` | HTTP | `prod-caddy:80` |
| `www` | `maxrommel.de` | HTTP | `prod-caddy:80` |

Both point at Caddy, which already has the routes loaded. Then:

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://maxrommel.de/   # expect 200
```

**Note for whoever tidies the dashboard later:** the compose file's header says
the dashboard is kept to a single wildcard rule so that `services.yml` stays the
source of truth. This adds two more, and that is deliberate — a wildcard covers
`*.maxrommel.de` but not the bare domain, which is a different DNS name and not
matched by it.
