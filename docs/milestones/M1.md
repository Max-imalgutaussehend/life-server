# M1 — Host baseline and SSH hardening

- **Date:** 2026-07-28
- **Status:** Complete, verified, idempotent
- **Playbook:** `make harden` (`ansible/site.yml`)

## What changed

| Area | Before | After |
|---|---|---|
| Login user | `root` | `deploy` (uid 1000), passwordless sudo |
| Root SSH | permitted | **disabled** |
| Password auth | enabled | **disabled** — key only |
| `AllowUsers` | any | `deploy` only |
| MaxAuthTries | 6 | 3 |
| Firewall | inactive | UFW active, `limit 22/tcp`, deny all other inbound |
| fail2ban | absent | active on sshd (5 fails/10 min → 1 h ban) |
| Swap | none | 2 GB, swappiness 10 |
| Timezone | UTC | Europe/Berlin |
| Docker | absent | 29.6.2 + Compose v5.3.1 |
| `/opt/life-server` | absent | owned by `deploy`, mode 0750 |
| Auto-updates | on, defaults | security-only, auto-reboot 04:00 |

## Why

**A non-root user with sudo, not root.** Every privileged action is attributable
in the auth log, and a compromised session is not automatically root.

**`ufw limit` rather than `allow`** (ADR-0013). Rate limiting costs nothing and
blunts credential stuffing. Port 22 closes entirely at M8.5 once Tailscale is
proven.

**The lockout rehearsal is a real SSH connection.** `roles/verify_access` opens
an actual session as `deploy` and runs `sudo -n id -u`, asserting uid 0, before
the security role runs. If it fails, the play aborts with root access intact.

**Swap on a 3.7 GB host** buys time before the OOM killer picks a container.
`swappiness=10` means it is only touched under real pressure.

## Three real bugs found — and how

Each was caught by verifying rather than assuming.

**1. cloud-init silently re-enabled password authentication.**
`/etc/ssh/sshd_config.d/50-cloud-init.conf` contains `PasswordAuthentication
yes`. sshd uses **first-match-wins**, and `50-` sorts before `99-`, so it beat
the hardening drop-in. Writing the file was not enough.
*Fix:* remove that file and set `ssh_pwauth: false` in
`/etc/cloud/cloud.cfg.d/` so cloud-init cannot recreate it on reboot.
*Caught by:* reading `sshd -T` (effective config) instead of trusting the file.

**2. `daemon.json` comments broke Docker.**
JSON has no comments, so `"//": "..."` keys were used. Docker rejects unknown
directives outright and refused to start. The `validate` step only checked JSON
syntax, not Docker's schema.
*Fix:* comment-free `daemon.json`; rationale moved into the Ansible task.

**3. `ansible_user=root` stopped working mid-milestone.**
Expected — the playbook disables the login it was using.
*Fix:* inventory switched to `ansible_user=deploy`.

## How to verify

```bash
# Root must be refused
ssh -i ~/.ssh/life-server root@<host-ip>
# expected: Permission denied (publickey,password)

# Deploy must work and reach root
ssh -i ~/.ssh/life-server deploy@<host-ip> 'id -u; sudo -n whoami'
# expected: 1000 / root

# Effective sshd config — the file is not proof, this is
ssh -i ~/.ssh/life-server deploy@<host-ip> \
  'sudo sshd -T | grep -E "^(permitrootlogin|passwordauthentication)"'
# expected: permitrootlogin no / passwordauthentication no

make harden      # second run must report changed=0
```

## Rollback

**Restore root SSH access** (from a working `deploy` session, or the console):

```bash
sudo rm /etc/ssh/sshd_config.d/99-life-server.conf
sudo rm /etc/cloud/cloud.cfg.d/99-disable-ssh-pwauth.cfg
sudo systemctl restart ssh
```

**Disable the firewall:** `sudo ufw disable`
**Stop fail2ban:** `sudo systemctl disable --now fail2ban`
**Remove swap:** `sudo swapoff /swapfile && sudo rm /swapfile`, drop the fstab line
**Remove Docker:** `sudo apt purge docker-ce docker-ce-cli containerd.io docker-compose-plugin`

**If locked out entirely:** Hetzner Cloud Console → VNC → log in as root with
the password → apply the first block above. This path does not depend on SSH,
Docker, or the firewall.

## Common failure cases

**`make harden` → UNREACHABLE, "root@... Permission denied".** The inventory
still says `ansible_user=root`. It must be `deploy` after M1.

**`sshd -T` still shows `passwordauthentication yes`.** Another drop-in in
`/etc/ssh/sshd_config.d/` sorts earlier. First match wins — list the directory.

**`docker: permission denied` as deploy.** Group membership needs a fresh
login. Reconnect.

**Docker fails to start after editing `daemon.json`.** Any unknown key makes
dockerd exit. `sudo journalctl -u docker -n 20` names the offending directive.

## Nachtrag 2026-07-29 — ssh.socket (kritisch)

**Symptom:** SSH verweigerte mitten in der Sitzung Verbindungen ("Connection
refused", nicht Timeout). `systemctl is-active ssh` meldete `active`, aber
`systemctl is-enabled ssh` meldete **`disabled`**.

**Bedeutung:** sshd lief nur noch bis zum nächsten Reboot. Danach wäre der
einzige verbleibende Zugang die Hetzner-Konsole gewesen.

**Ursache:** Ubuntu 24.04 nutzt standardmäßig Socket-Activation — `ssh.socket`
besitzt Port 22 und startet `ssh.service` bei Bedarf. Die security-Rolle
verwaltete `ssh.service` direkt und hat diese Konstellation ignoriert. Jeder
Dienst-Neustart öffnete ein Fenster, in dem Verbindungen abgelehnt wurden.

**Fix (in der Rolle, nicht von Hand):** Socket-Activation wird bewusst
abgeschaltet und das klassische Modell erzwungen —
`ssh.socket` gestoppt und disabled, `ssh.service` enabled und started, gefolgt
von einer Assert-Task, die `is-enabled` prüft. Ein Server, der dauerhaft sshd
braucht, gewinnt durch Socket-Activation nichts.

**Diagnose-Merkregel:** *refused* heißt, das Paket kam an und niemand lauschte
(Dienst unten). *Timeout* heißt, es wurde verworfen (Firewall/fail2ban). Der
Vergleich mit Port 80/443 — dort Timeout — hat fail2ban und UFW ausgeschlossen.

**Nebenbefund:** fail2ban hatte zwischenzeitlich die eigene Arbeits-IP gebannt
(zu viele Verbindungen in Folge). Selbstkorrigierend nach der Bannzeit, aber
bei Automatisierung gegen den Host zu beachten.
