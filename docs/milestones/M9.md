## The constraint that shapes everything

**A Claude subscription authenticates Claude Code interactively. It is not a
credential a daemon can present to call the Anthropic API in a loop.**

So "Hermes as a long-running service that calls the API" is not buildable here —
not rejected on taste, simply without a mechanism. The operator anticipated this
(*"if not possible with hermes then just claude code & paperclip"*).

**The runtime therefore becomes Claude Code itself**, headless, with Paperclip
owning the tickets and invoking sessions.

## What was built

| Area | Delivered |
|---|---|
| Schema | `compose/postgres/migrations/paperclip/001-tickets.sql` |
| Runner | `scripts/migrate.sh` — checksummed, idempotent, service-role |
| Make | `make migrate DB=paperclip [MODE=--status\|--dry-run]` |

### Why a migration runner had to come first

`compose/postgres/initdb/` **only runs when the Postgres volume is empty.** It
has been unable to change anything since M4. Without a migration path, every
schema change becomes hand-typed `psql` — unreproducible, unreviewable, and the
repository stops describing the system.

`migrate.sh` applies each file once, as the **service role** rather than the
superuser, so objects belong to the role that has to live with them (ADR-0005).

**Applied migrations are checksummed.** Editing a file that already ran is a hard
error, because the database reflects the old content while the repo shows the
new and nothing would ever re-run it. Verified by appending a line to an applied
migration: `DRIFT` reported, exit code 1, clean again once reverted.

### Invariants live in the database

Each was verified by trying to violate it:

| Attempt | Rejected by |
|---|---|
| blank title | `tickets_title_check` |
| `status='claimed'` with no `claimed_by` | `ticket_claimed_has_owner` |
| `status='nonsense'` | enum type |
| `parent_id = id` | `ticket_not_own_parent` |

Also verified: the `updated_at` trigger fires, `ticket_events` accepts `jsonb`
payloads, and deleting a ticket cascades to its events. Test rows removed.

`claimed` without a claimant earns its own constraint: it looks like work in
progress and is nobody's, which is how a queue stalls without anyone noticing.

## The security boundary, before any agent runs

The operator requires agents that **execute code**. On a host that also holds
Postgres, `.env`, the age key and the backup repository, that means any prompt
reaching an agent could read every secret the system has. This is not a
hypothetical; it is the plain consequence of code execution plus co-location.

Step 2 is therefore the sandbox, **before** step 3 runs a single agent:

| Rule | Reason |
|---|---|
| Non-root user, one container per session | a compromised session is not a compromised host |
| Joins neither `data` nor `edge` | no route to Postgres, Redis or the tunnel |
| No bind mount of the repo, `.env`, age key, or the Docker socket | the socket is root on the host, trivially |
| DB access only via an explicit API on `apps` | the agent gets an interface, not credentials |

Retrofitting an isolation boundary under a running system is how boundaries end
up with holes.

### Step 2 is built and proven

A fourth network, `net-agent`, deliberately separate from `apps`. Anything on
`apps` can open a socket to anything else on `apps` — so putting agents there
would let a prompt-injected session talk to n8n, which holds credentials for
every service it integrates with.

`scripts/verify-agent-sandbox.sh` starts a probe container on that network as
uid 65534 and *attempts* what an escaped agent would attempt. All 15 assertions
pass:

| Attempted | Result |
|---|---|
| `postgres:5432`, `redis:6379` (both name forms) | unreachable |
| `prod-n8n:5678`, `prod-caddy:80`, `prod-ntfy:80`, `prod-status:3001` | unreachable |
| `/var/run/docker.sock` | absent — a mounted socket is host root in one call |
| `.env`, `secrets.enc.env`, the age key | not visible |
| running as root | no, uid 65534 |
| egress to `api.anthropic.com:443` | **works** — required, or Claude Code cannot function |

**The negative control matters more than the passes.** A test that cannot fail
proves nothing, so an identical probe was started on `net-data`: it *did* reach
`postgres:5432`. The isolation is real, not a broken probe.

`deploy.sh` now creates `net-agent` idempotently, because Compose only creates
networks a declared service joins — and agent workspaces are started per session
by `docker run`, not declared here.

**The threat model is prompt injection, not a malicious operator.** An agent
reads a web page, an email, or a ticket written by another agent, and that text
tells it to exfiltrate `.env`. The agent is not compromised; it is working
correctly on hostile input. So nothing in the workspace may be worth stealing.

**The open design question:** Claude Code's OAuth session lives on the machine
where the login happened. Running it in a throwaway container means either
mounting that credential in (contradicting the table above) or logging in per
session (interactive, defeating automation). This must be solved before step 3,
and it is a design question, not an implementation detail.

## Undo

```sql
DROP TABLE IF EXISTS ticket_events, tickets;
DROP TYPE  IF EXISTS ticket_status, ticket_priority;
DELETE FROM schema_migrations WHERE filename = '001-tickets.sql';
```

Nothing else in the system references these tables yet, so this is a clean
removal.

## Still open

- **The "work agent"** — what it is and how it connects (inbound webhook,
  outbound polling, shared queue). Determines whether anything new must be
  publicly reachable. Nothing is built for it until answered.
- **Concurrency and cost** — how many sessions may run at once. A subscription
  has rate limits and an unbounded delegation tree will find them.
