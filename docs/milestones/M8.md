## Proven, not assumed

The whole point of monitoring is that it fires when something breaks, so it was
tested by **breaking something**: `prod-whoami` was stopped and the chain was
followed all the way to a delivered notification.

| Step | Result |
|---|---|
| Kuma detects the outage | ✅ DOWN after ~3 min (60s interval + 2 retries) |
| Alert published to ntfy | ✅ `whoami Down [Uptime-Kuma]`, priority 5 |
| Alert carries the cause | ✅ `connect EHOSTUNREACH 172.20.0.3:8000` |
| Recovery notification | ✅ `whoami Up`, priority 4, on restart |
| All monitors green afterwards | ✅ caddy, n8n, ntfy, whoami all UP |

A dashboard showing green is not evidence. A delivered alert is.

## Why monitors are checked internally

Every monitor targets a **container name on the apps network**
(`http://prod-caddy:80/healthz`), never the public hostname.

A public check would be intercepted by Cloudflare Access, and a 302 to a login
page is not a health signal — it measures the gate, not the service. Worse, it
would report "up" whenever Access is working even if the service behind it is
dead.

## Why monitors are seeded from code

Uptime Kuma is configured by clicking, and clicking is configuration drift — the
same objection ADR-0008 raises against Portainer. Without seeding, a service
added to `services.yml` silently goes unmonitored until somebody remembers to add
it in the UI, and "we thought it was monitored" is worse than knowing it is not.

`make seed-monitors` is idempotent: it reuses the existing notification channel
and skips monitors that already exist, so it is safe to re-run after adding a
service.

## ntfy is locked down by default

`auth-default-access: deny-all` in `compose/ntfy/server.yml` is the load-bearing
line. ntfy's default is read-write for everyone, which on a reachable host means
anyone can both **read your alerts and forge them**.

Three identities, least privilege:

| User | Rights | Why |
|---|---|---|
| `max` | admin | operator; owns the topic |
| `kuma` | **write-only** on the alert topic | a compromised Kuma can publish alerts but cannot read them or touch other topics |
| anonymous | nothing | verified: `403 forbidden` on publish |

The phone uses an access token (`NTFY_PHONE_TOKEN` in `.env`) rather than a
password, so it can be revoked without changing the account.

## The setup-wizard exposure, again

Uptime Kuma shipped the **same** problem n8n did in M6: an anonymous visitor was
redirected to `/setup-database`, where the first arrival picks the database and
creates the admin account.

Closed the same way — internally, before anyone else could:

1. `POST /setup-database` with `{"dbConfig":{"type":"sqlite"}}` over `localhost`
2. admin row inserted using **Kuma's own** `password-hash.js` (bcryptjs, 10
   rounds) and its bundled `@louislam/sqlite3` driver — not a reimplementation
3. verified with Kuma's own `verify()` that the password in `.env` matches the
   stored hash

`GET /` now redirects to `/dashboard`, not `/setup-database`. Credentials are in
`.env` as `KUMA_ADMIN_USER` / `KUMA_ADMIN_PASSWORD`, and in both backup tiers.

**Pattern worth remembering:** self-hosted services routinely ship a
first-run-claims-ownership wizard. Any new service must be assumed to have one,
and the owner claimed before the hostname is publicly routable — the tunnel's
wildcard means "deployed" and "reachable" happen simultaneously.

## Three bugs found while building this

**1. Healthchecks assumed a toolset the images lack.** My Kuma healthcheck used
`wget`; the Kuma 2.x image ships `curl` and no `wget`, so the probe reported the
service unhealthy while it was fine. The ntfy image has neither, so its test uses
the `ntfy` binary. Lesson: check what the image actually contains rather than
assuming busybox.

**2. `monitor.conditions` is NOT NULL in Kuma 2.x.** Monitor creation failed with
`SQLITE_CONSTRAINT`, and because the error arrived only in the Socket.IO callback
the script appeared to "time out" — a misleading symptom for a straightforward
schema requirement. Fixed by sending `conditions: []`, and the script now reports
per-monitor failures instead of hanging.

**3. Deleting duplicate notifications orphaned the monitor links.** Cleaning up
duplicate channels left rows in `monitor_notification` pointing at deleted
notifications, so Kuma detected the `whoami` outage and sent **nothing** — the
worst possible failure for a monitoring system, since it looks like everything is
fine. Found only because the outage test checked for a *delivered message*
rather than a *detected outage*. Repaired by re-pointing every monitor at the
surviving channel, then re-running the full outage test.

Also worth noting: `getMonitorList` and `notificationList` are **pushed events**
in Kuma 2.x, not callback-returning calls. Reading them from a callback returned
`undefined`, so everything looked absent and a second seeding run duplicated all
four monitors plus the channel. The script now listens for the events.

## Known limitation: who watches the watchman

Kuma runs inside the stack it monitors. **If the host or Docker dies, Kuma dies
with it and sends nothing.** It reliably catches one service failing — the common
case — but cannot report its own death.

The honest complement is an external check, which is listed as follow-up:

- a free external monitor (Uptime Robot, Healthchecks.io) hitting
  `https://status.maxrommel.de` or Caddy's `/healthz`
- Healthchecks.io watching the backup timer, which also closes ADR-0009's
  "alert on backup failure" item

```bash
  docker compose -f compose/docker-compose.prod.yml rm -sf status ntfy'
```

`make deploy-stack`. Volumes survive. Nothing in M1–M7 depends on M8.
