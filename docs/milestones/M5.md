# M5 — Backups

- **Date:** 2026-07-30
- **Status:** ✅ Complete. Two tiers: automated daily on the server, plus an
  on-demand off-host copy on the operator's laptop, verified restorable there.
  M6 unblocked. Caveat: the off-host copy is only as fresh as the last pull.

## What changed

| Area | Delivered |
|---|---|

## What is in the backup set, and why

| Item | Reason |
|---|---|
| `pg_dumpall` output | A file-level copy of a **running** Postgres is not crash-consistent. A logical dump is consistent by definition, so the database is dumped, never copied (ADR-0009). |
| `.env` | Not in Git (ADR-0006). Without it, a total loss means regenerating every secret and losing every credential n8n stores. The easiest item to forget, the most expensive to lose. |
| Docker volumes | Redis AOF/RDB, Caddy data, later app volumes. |
| Repo checkout | Cheap; makes a bare-metal rebuild one restore instead of a clone plus setup. |

Postgres' **data directory is deliberately excluded** — the dump supersedes it.
Keeping both would double the size and invite restoring the wrong one.

## Why systemd timers, not cron

A failed cron job mails someone who isn't reading it. A failed systemd unit
shows up in `systemctl --failed`, keeps its output in the journal, and gives M8
exactly one thing to alert on. `Persistent=true` also reruns a backup missed
while the host was down; cron would simply skip the day and say nothing.

## The bug the verification caught

The first backup **reported failure**: `snapshot is missing /opt/life-server/.env`.

`.env` was in fact in the snapshot. The defect was in my check, which ran a
separate `restic ls latest | grep -q` per path. `grep -q` exits on first match,
closing the pipe and killing `restic ls` with SIGPIPE mid-read; that left the
repository lock in a state where the *next* invocation returned nothing — so the
dump passed and `.env` produced a false alarm.

Fixed by listing once into a file and grepping that file repeatedly: no repeated
locking, no SIGPIPE, no false alarm.

Worth keeping in mind: **the assertion was wrong, but writing it was still
right.** A check that cries wolf gets found and fixed on day one. A missing
check gets found during a restore. What made it debuggable was that the script
named the exact path it thought was absent.

## Two tiers, and why

`RESTIC_REPOSITORY=/srv/restic` alone is **on the same disk as the data it
protects** — it survives an accidental `DROP TABLE` or a bad deploy, but not
disk failure, host loss, or account loss. ADR-0009 rejected exactly that as a
strategy, so a second tier carries the off-host requirement:

| Tier | Where | Trigger | Survives |
|---|---|---|---|
| 1 | `/srv/restic` on the server | systemd, daily 02:30 | bad deploy, data mistake |
| 2 | `~/life-server-backups/restic` on the laptop | `make backup-pull` | disk, host, and Hetzner account loss |

Tier 2 is different hardware, in a different building, on a different
provider's account — which is what "off-host" is actually asking for.

**Why the laptop pulls instead of the server pushing.** A laptop is not always
on. A server pushing to it at 02:30 would fail most nights, and a backup that
routinely fails trains you to ignore it — the "silently broken backup is worse
than none" failure ADR-0009 warns about. Pulling means a run either works or is
genuinely worth reading.

**Why rsync and not `restic copy`.** A restic repository is content-addressed,
so rsync transfers only new packs and the result is a byte-identical repository
this machine's own restic can open, check and restore from with the server
absent. `restic copy` would re-encrypt into a second repository with different
IDs — slower, and harder to reason about during a recovery.

**`--delete` is deliberately NOT used.** A repository damaged or truncated on
the server must not propagate that damage into the only off-host copy. Extra
local packs are harmless (restic ignores unreferenced data); silently deleted
ones are unrecoverable.

### The honest limitation

**The off-host copy is only as fresh as your last pull.** Between pulls, tier 1
is the only protection. `make backup-pull-status` reports the age and exits
non-zero past seven days, so the gap is visible rather than assumed:

```
Local off-host copy : /Users/I751109/life-server-backups/restic
Size                : 192K
Last pull           : 2026-07-30T01:45:44Z (0 days ago)
```

A cloud remote (Backblaze B2, Hetzner Storage Box) would remove that caveat by
making tier 2 automatic. Kept as a future option, not a blocker — set
`RESTIC_REPOSITORY` to `s3:...` or `sftp:...` and the same scripts work
unchanged.

## Operating notes

```bash
make backup                 # run a server-side backup now
make restore                # REHEARSE a restore (safe, throwaway database)
make restore-list           # list snapshots
make backup-status          # timer schedule + last run's result

make backup-pull            # copy the repository to THIS machine (off-host)
make backup-pull-verify     # pull, then prove the local copy is restorable
make backup-pull-status     # how stale is the off-host copy?
```

**Run `make backup-pull` regularly** — weekly is a reasonable habit, and after
any change you would hate to redo. It is the only tier that survives losing the
server.

Real recovery, deliberately not wrapped in a make target so it cannot be run
by reflex:

```bash
# recover files (e.g. a lost .env) — never touches Postgres
sudo /opt/life-server/scripts/restore.sh --files /tmp/recovered

# overwrite the live database — asks you to type RESTORE
sudo /opt/life-server/scripts/restore.sh --db-production --snapshot <id>
```

**`RESTIC_PASSWORD` belongs in your password manager now.** Losing it makes
every snapshot permanently unreadable — there is no recovery path, by design.

## Rollback

```bash
ssh -i ~/.ssh/life-server deploy@62.238.4.64 '
  sudo systemctl disable --now life-server-backup.timer life-server-backup-check.timer'
```

Stops all scheduled backups; snapshots and `/srv/restic` survive. To remove the
units entirely, delete `/etc/systemd/system/life-server-backup*` and
`systemctl daemon-reload`. Nothing in M1–M4 depends on this milestone.

## ADR-0009 follow-ups

- [x] restic container and repository — host package, not a container (see below)
- [x] verify `.env` is in the backup set — asserted on every run
- [x] **rehearse a restore against a throwaway database** — passing
- [x] document the restore procedure step by step
- [x] **move the repository off-host** — laptop tier, restore-verified there
- [ ] M8: alert on backup failure via ntfy
- [ ] optional: automate tier 2 with a cloud remote, removing the freshness caveat

**Deviation from ADR-0009, recorded:** it anticipated a restic *container*. This
runs restic as a host package under systemd instead. A container would need the
Docker socket plus host mounts to read volumes and dump Postgres — a larger
attack surface than a root script on a timer, for no benefit. The ADR's intent
(scheduled, monitored, encrypted, off-host) is unaffected.
