# M8.5 — SSH over Cloudflare Access, and closing port 22

- **Date:** 2026-07-31
- **Status:** 🔶 **Designed and documented. Not activated.** Port 22 is still
  open, deliberately — see "Why this stopped here".

## Why this stopped here

The operator went offline mid-milestone. Closing the only working access path
needs two things that cannot be done without them:

1. **The three-step verification** (connect → fully disconnect → reconnect cold)
   has to be performed from the operator's own machines, with their own Access
   login. Nobody else can authenticate as them, so nobody else can prove the
   replacement path works for them.
2. **The console fallback must be real.** ADR-0013 and ADR-0016 both make the
   Hetzner Cloud Console the permanent last resort, and its only precondition is
   the root password. That password is not in `.env`, not in the repository, and
   not verifiable from this machine.

Closing port 22 on an unverified fallback, with nobody reachable, is exactly the
failure ADR-0013 was written to prevent. So the port stays open.

**Current posture is unchanged and still sound:** `ufw limit 22/tcp`, key-only
authentication, root login disabled, fail2ban active. This has held since M1
against roughly 1000 automated attempts a day.

## The finding that changed the plan

The intended implementation was to add an `ssh://` ingress rule to
`generator/templates/cloudflared-config.yml.j2`, regenerate, deploy.

**That would not have worked, and worse, it would have looked like it did.**

`compose/docker-compose.prod.yml` runs cloudflared with `TUNNEL_TOKEN`, which is
token-managed mode: cloudflared fetches ingress rules from the Cloudflare
dashboard and **never reads the generated config file**. The file is not even
mounted into the container. An SSH rule added there would have been a
convincing, committed, reviewed, entirely inert piece of configuration.

A second error was caught at the same time: the draft rule used
`ssh://127.0.0.1:22`, which would only be correct if cloudflared ran with
`network_mode: host`. It does not — it is on the `edge` network, where
`127.0.0.1` is the container's own loopback and no sshd is listening.

Both are now documented in the template's header so the next person does not
repeat them.

## What the operator must do

### 1. Add the SSH route (dashboard, ~2 min)

Because the tunnel is token-managed, this is a dashboard change, not a config
change.

Cloudflare Zero Trust → **Networks** → **Tunnels** → your tunnel → **Published
application routes** → *Add a published application route*:

| Field | Value |
|---|---|
| Subdomain | `ssh` |
| Domain | `maxrommel.de` |
| Type | **SSH** |
| URL | `localhost:22` |

⚠️ **`localhost:22` will almost certainly NOT work as written**, and this is
worth understanding before trying it.

cloudflared runs in a container on the `edge` network. Inside that container,
`localhost` is the container itself, where no sshd listens. The host's sshd is
not reachable from there by that name.

Two options, in order of preference:

1. **Use the Docker bridge gateway**: set the URL to `172.17.0.1:22`. Confirm
   the address first — `docker network inspect bridge -f '{{(index .IPAM.Config 0).Gateway}}'`.
2. **Give cloudflared a host alias**: add
   `extra_hosts: ["host.docker.internal:host-gateway"]` to the cloudflared
   service in `compose/docker-compose.prod.yml`, redeploy, and use
   `host.docker.internal:22`.

Option 2 is more explicit and survives a change of bridge subnet, so prefer it
if you are editing compose anyway.

**A second correction to the step above.** The compose file's own header records
that the dashboard is deliberately kept to *one wildcard rule pointing at
Caddy*, so that `services.yml` stays the single source of truth (ADR-0014).
Adding a per-hostname SSH route is a deliberate exception to that rule — SSH is
TCP and cannot go through Caddy — but it does mean the dashboard now holds two
rules instead of one. Note it, so the next person does not "tidy it up".

### 2. Add the Access application (dashboard, ~2 min)

Zero Trust → **Access** → **Applications** → *Add an application* →
**Self-hosted and private**:

| Field | Value |
|---|---|
| Application name | `ssh` |
| Destination | Public hostname `ssh` . `maxrommel.de`, path empty |
| Session Duration | **`1 hour`** |
| Policy | Allow → Include → **Emails** → `max.rml@web.de` |

**One hour, not 24 and not a month.** This application grants a shell. The other
applications sit in front of a service that has its own login; this one is the
front door.

### 3. Configure the client

`brew install cloudflared` on each machine, then add to `~/.ssh/config`:

```
Host life-server
    HostName ssh.maxrommel.de
    User deploy
    IdentityFile ~/.ssh/life-server
    ProxyCommand cloudflared access ssh --hostname %h
```

The command stays `ssh life-server`. Muscle memory and every existing script
keep working.

### 4. Verify — twice, cold (this is the gate)

```bash
ssh life-server 'hostname; uptime'          # 1. connect
exit
ssh -O exit life-server 2>/dev/null || true # 2. drop any multiplexed socket
pkill -f 'cloudflared access ssh' || true   #    and the proxy process
ssh life-server 'hostname'                  # 3. reconnect cold
```

A path that works while a warm connection or a `ControlPersist` socket exists
proves nothing about the path needed when everything is cold.

### 5. Confirm the fallback, then close

**Before running the close command,** confirm the Hetzner root password is in
Bitwarden. It is the console's only precondition, and the console is what
remains if Cloudflare is unreachable.

```bash
ssh life-server                        # over Access, one last time
sudo ufw delete limit 22/tcp
sudo ufw status
```

Then, from a machine with no Access session, confirm it is really shut:

```bash
nc -vz 62.238.4.64 22                  # must time out or be refused
```

## Undo

If Access SSH misbehaves and the console is available:

```bash
sudo ufw limit 22/tcp
```

One line, and sshd was never reconfigured — which is the point of routing to
`localhost:22` rather than changing how sshd binds.

## What this achieves when finished

Zero public inbound ports. Web traffic and SSH both arrive through an
outbound-initiated tunnel; nothing on the internet can initiate a connection to
this host. Combined with ADR-0016's two independent factors — Access
authenticates the person, the SSH key authenticates the session — an attacker
needs to defeat Cloudflare Access *and* hold a private key.
