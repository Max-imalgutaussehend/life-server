## ⚠️ The one thing you must do

**n8n is stopped, deliberately.** When it was first started it served its setup
page to the open internet, and `showSetupOnFirstLoad` was `true` — meaning
**anyone who found the URL could have claimed the owner account.** No data was
at risk (the instance was empty), but the window was real and is now closed.

`access: private` in `services.yml` is a *declaration*. ADR-0003 is explicit
that Access policies live in the Zero Trust dashboard and **cannot** be
expressed in config, so nothing in this repository can create one. It is a
manual step that must be audited.

### Create the policy

1. Cloudflare Zero Trust → **Access** → **Applications** → *Add an application*
2. Type: **Self-hosted**
3. Application domain: `n8n` . `maxrommel.de`
4. Session duration: **24 hours** (or up to 30 days for convenience on mobile)
5. Add a policy:
   - Action: **Allow**
   - Rule: *Emails* → `max.rml@web.de`
   - Optionally also *Login Methods* → Google, if you prefer that to email codes
6. Save.

### Then start n8n

```bash
make deploy-stack
```

### Verify the policy actually works — do not skip this

```bash
# Must NOT return 200. Expect 302 to the Cloudflare login.
curl -s -o /dev/null -w '%{http_code}\n' https://n8n.maxrommel.de/

# Must NOT be reachable anonymously.
curl -s https://n8n.maxrommel.de/rest/settings | head -c 100
```

A `200` with n8n's HTML means **the policy is not applied** and the instance is
public. Stop it again (`docker compose stop n8n`) and re-check the dashboard.

From your phone or laptop the flow is: open the URL → Cloudflare login page →
email code (or Google) → session cookie → n8n. No VPN, no client software, which
is why this replaces Tailscale (see ADR-0013's constraint note).

## Why these settings

**`N8N_PROTOCOL: https` while the internal hop is plain HTTP.** These variables
describe the *public* scheme, and n8n uses them to build webhook and OAuth
callback URLs. Setting `http` here produces webhooks pointing at a URL that
external services cannot reach — a failure that only surfaces later, when a
third party tries to call back. Cloudflare terminates TLS (ADR-0003).

**`EXECUTIONS_DATA_PRUNE` with a 14-day window.** n8n's execution history grows
without limit by default. Left alone it comes to dominate both the database and
every backup taken of it. Failures and successes are both retained inside the
window; progress data is not, because it is the bulkiest and least useful.

**`N8N_ENCRYPTION_KEY` is the single most important variable in `.env`.** It
encrypts every credential n8n stores. Lose it and every stored credential is
unrecoverable — which is exactly why ADR-0009 insists `.env` is in the backup
set, and why the M5 laptop tier matters.

**`NODES_EXCLUDE` blocks filesystem and command-execution nodes.** n8n will be
reachable by one authenticated operator, but "read any file on the host" is a
capability nothing planned here needs, so it is removed rather than trusted.

**Not using queue mode.** Redis is running and available, but a single-instance
n8n with one operator does not need a separate worker process; queue mode would
add a container and a failure mode for no current benefit. Redis stays ready for
when a workload actually justifies it.

## The bug this milestone found: Caddy served a stale config

`n8n.maxrommel.de` returned the catch-all **404** after deployment, despite the
route being present in the generated Caddyfile on the server.

The Caddyfile is **bind-mounted**. Changing it on disk does not change the
container's definition, so `docker compose up -d` sees nothing to do and Caddy
keeps serving the config it loaded at startup. `caddy adapt` confirmed it:

```
on-disk Caddyfile:  6 matches for "n8n"
loaded config:      only whoami.maxrommel.de
```

`caddy reload` then failed with `connect: connection refused` on port 2019 —
because the Caddyfile sets `admin off`, deliberately. With no admin API, the
supported path is restarting the container.

`deploy.sh` now compares the on-disk Caddyfile's hash against the one inside the
running container and restarts Caddy only when they differ. A routine deploy
does not bounce ingress; a routing change does.

**This is the M3 lesson recurring:** effective configuration beats intended
configuration. The file was right and the system was wrong, and only asking the
running process what it had loaded revealed it.

## Rollback

```bash
ssh -i ~/.ssh/life-server deploy@62.238.4.64 'cd /opt/life-server && \
  docker compose -f compose/docker-compose.prod.yml rm -sf n8n'
```

Set `enabled: false` for `n8n` in `services.yml`, `make generate`, then
`make deploy-stack` to remove the route. The volume and the `n8n` database
survive; nothing in M1–M5 depends on n8n.
