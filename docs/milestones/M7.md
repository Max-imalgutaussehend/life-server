# M7 — Secrets in Git, and CI that enforces the invariants

- **Date:** 2026-07-29 (SOPS) / 2026-07-31 (CI half)
- **Status:** ✅ Complete. All three `validate` jobs green on every push.

## What changed

| Area | Delivered |
|---|---|
| Secrets | `.env` encrypted to `secrets.enc.env`, committed (ADR-0006 Phase 2) |
| Keys | Two age recipients — operator and CI — that decrypt **independently** |
| CI | `.github/workflows/validate.yml`, read-only, no server access |
| Lint config | `.yamllint.yml`, which the repo never had |
| Make | `secrets-encrypt`, `secrets-decrypt`, `secrets-edit`, `secrets-verify` |

## Two keys, not one shared key

ADR-0006 required GitHub Actions to get its **own** age key rather than a copy of
the operator's. The reason is revocation. With a shared key, a leaked CI key
means rotating the operator's key, re-encrypting, and re-distributing. With two
recipients, revoking CI is:

```bash
# delete CI's line from .sops.yaml, then
sops updatekeys secrets.enc.env
```

The operator's key is untouched and nothing they hold needs re-encrypting.

Both keys were verified to decrypt the same file separately — 24 variables each.
Verifying only that "sops works" would have proven nothing about the second
recipient.

## Only values are encrypted

Key *names* stay plaintext inside `secrets.enc.env`. This is deliberate: a diff
shows **which** secret changed without revealing any value, so rotation stays
auditable in Git history.

## What CI actually checks

Four invariants, each one a mistake that is cheap to make and expensive to find:

| Check | Failure it prevents |
|---|---|
| `render.py --check` | committed config that no longer matches `services.yml` (ADR-0014) |
| no `:latest` in `compose/` | an unpinned image (ADR-0011) |
| no `.env` / age key tracked | a real secret in Git |
| `sops --decrypt` with CI's key | **CI silently losing its recipient status** |

The last one is why the workflow exists. That failure is invisible: someone
re-encrypts without `sops updatekeys`, CI stops being a recipient, and nothing
looks wrong until a restore — the worst possible moment to discover it. A check
on every push turns it into a red build.

The decrypt step **counts** variables and discards them. Values are never
printed, written to a file, or exposed as a step output.

## What CI deliberately does not do

**It does not deploy.** Per ADR-0007 the server pulls. CI holds no SSH key and
cannot reach the host, so a compromised Actions run can at worst make this check
lie — it cannot change production.

**There is no GHCR build job.** All eight images are pinned third-party images
and the repository contains no Dockerfile. A build job would have nothing to
build. This was reconsidered when the remote appeared, and rejected on the facts.

`permissions: contents: read` means a compromised action cannot push to `main`.

## Three things found by running it, not by reading it

**1. The ansible check was passing vacuously.** It referenced `inventory.yml`;
the file is `inventory.ini`. `--syntax-check` parsed an empty inventory and
reported success — a green check that verified nothing. It now runs from
`ansible/` so `ansible.cfg` applies.

**2. `make lint` skips missing linters.** Correct on a laptop, wrong in CI: a
skipped check that reports success is worse than no check at all. CI installs
the linters and calls them directly.

**3. There was no yamllint config.** The 80-column default failed three lines
that are right as written — a role-ordering comment, a copy-pasteable `ssh`
hint, and an unwrappable Jinja expression. The cap is now 100 and still an
error. `.github/` is linted too, since CI's own config gets no exemption from
the rules it enforces; that immediately caught a 113-character line in the
workflow itself.

On shellcheck, `--severity=warning`. All four findings were SC2001 style hints
about `sed 's/^/  /'` indenting a **multi-line** string, where the suggested
`${var//search/replace}` does not do per-line prefixing. Complying would have
made the code worse to satisfy a linter. SC2086 word splitting and SC2164
unchecked `cd` are warning-or-above and still fail the build.

## Verify

```bash
make secrets-verify                    # encrypted file round-trips to live .env
gh run list --limit 3                  # all jobs green
gh secret list                         # SOPS_AGE_KEY present
```

## Undo

```bash
git rm .github/workflows/validate.yml  # CI only; changes nothing on the server
gh secret delete SOPS_AGE_KEY
```

Removing SOPS itself is a larger step: `.env` on the server is the file every
tool reads and is unaffected, but `secrets.enc.env` would stop being maintained
and the repo would no longer be recoverable without a copy of `.env`.

## The gap this closes

Before M7 the server was **not** reproducible from Git — a total loss needed the
repo *and* a copy of `.env`, which ADR-0006 flagged as a deliberate, bounded
gap. That gap is now closed for anyone holding either age key.
