# M11 — Upstream Paperclip, two agent runtimes, one subscription

**Status:** deployed 2026-08-01 — sandbox 20/20, awaiting the operator's proxy login
**ADR:** [0020](../adr/0020-upstream-paperclip-and-subscription-proxy.md) (supersedes 0019 and 0018)

## What changed

M9/M10 built a Go ticket UI and a shell agent runner. Both are gone. The real
Paperclip product replaces them, and the architecture becomes two points of
contact:

1. **OpenClaw** — the personal assistant, reachable on WhatsApp, which talks to
   Paperclip.
2. **Hermes** — the CEO agent, whose sub-agents you build in the Paperclip UI.

Both run on the operator's Claude subscription through a single proxy.

## The shape of it

```
WhatsApp ──> openclaw ─┐
                       ├──> cliproxy ──> Claude (subscription OAuth)
paperclip ──> hermes ──┘
     │
     └──> postgres          [net-data]

net-agent : cliproxy, openclaw, hermes, paperclip, cliproxy-heartbeat
net-apps  : paperclip, n8n, status, ntfy, caddy, cliproxy-heartbeat
```

`cliproxy-heartbeat` is the only container on both `agent` and `apps`. That is
deliberate and is explained under Monitoring.

## Decisions worth knowing

### Paperclip is built by CI, not on the server

Upstream publishes no server image — GHCR under `paperclipai/` holds only the
`agent-runtime-*` sandboxes. The root Dockerfile builds a pnpm monorepo plus a
UI, which does not fit in the memory this host has free.

`.github/workflows/paperclip-image.yml` builds it and pushes to our GHCR; the
server pulls a **digest**. ADR-0007 still holds: pushing an image is not
deploying one.

### Hermes uses the gateway adapter, not `hermes_local`

Upstream's `docker/agent-runtime/Dockerfile.hermes` is a stub. Its own comment:

> Until then, runs targeting hermes_local on the cloud adapter will boot the
> container but `agent-shim` will fail with "hermes not on PATH"

`hermes_gateway` is the supported path and has no such gap.

### Neither runtime is in `services.yml`

That registry generates PUBLIC routes. A public route to a container that runs
model-chosen code is an unauthenticated RCE endpoint. Both runtimes live on
`net-agent` and are reached over internal DNS.

## The memory budget

Measured with `docker stats` on 2026-08-01 — 596 MB actually in use across 9
containers, while caps totalled 3840 MB on a 3819 MB host. Caps are ceilings,
not reservations, so that was not broken; it did mean the kernel rather than
the config would choose a victim under pressure.

| service | was | now | measured | why |
|---|---|---|---|---|
| postgres | 1280M | 768M | 89M | ceiling is shared_buffers + work_mem x conns |
| redis | 512M | 320M | 13M | must stay above the 256M `maxmemory` |
| n8n | 1024M | 512M | 297M | |
| status | 384M | 384M | 120M | left alone — it reports the other failures |
| whoami | — | gone | 3M | also the only public endpoint here |
| paperclip | — | 640M | 361M | measured 2026-08-02 after 9h uptime |
| cliproxy | — | 256M | — | Go HTTP proxy |
| openclaw | — | 512M | — | Node + messaging session |
| hermes | — | 512M | — | Python agent runtime |
| heartbeat | — | 32M | — | a shell loop |

**All caps are now measured.** Paperclip settled at 361 MB against its 640M
cap after 9 hours; the cap is kept above steady state because agent sessions and
hourly backups are the peak, not the floor. Total real use is ~1.2 GB of 3.8 GB.
The sum of caps still exceeds physical RAM, which is safe only because caps are
ceilings rather than reservations.

## Monitoring: the part that matters

The Claude OAuth credential expires in **roughly 7 days**. When it does, every
agent stops silently — indistinguishable from an empty queue.

An HTTP check on `/health` would not catch it: the proxy answers `/health`
happily with a dead credential, i.e. it reports success during the precise
outage it was added to detect.

So `cliproxy-heartbeat` sends one **real completion** per hour (`max_tokens: 1`)
and pushes the result to a Kuma **push** monitor. It reports UP only if the
model actually answered.

The push direction is not an implementation detail. Kuma polling into
`net-agent` would let every agent session reach Kuma — and Kuma holds the ntfy
publish token, i.e. the ability to send a forged all-clear. M8 established that
the all-clear is the one message that must stay trustworthy. The heartbeat
bridges the two networks instead, which is safe because it runs a fixed script
and never executes model-chosen code. `verify-agent-sandbox.sh` still asserts
that agents cannot reach `status`, which is what keeps that distinction real
rather than aspirational.

## Known gaps

- **The proxy is unsupported.** A third-party wrapper around an OAuth flow
  Anthropic can change without notice. Expect to maintain it.
- **Weekly re-auth is manual.** `make proxy-login` needs a browser. There is no
  headless path.
- **OpenClaw's WhatsApp route is not yet configured** — it needs a public
  callback, which needs two Cloudflare Access applications. See
  OPERATOR-TASKS.md. Until then the route stays disabled.
