## Why

**No published ports.** Not one service declares `ports:`. Traffic arrives only
through the outbound tunnel, so UFW still needs no rule for 80/443 (ADR-0003).

**A `caddy` network alias.** The tunnel's dashboard rule targets `caddy:80`.
The alias makes that resolve to `prod-caddy` or `dev-caddy` without the rule
knowing the environment prefix.

**Prefixes derived, not declared.** `ENV_PREFIX` is computed from `ENV` on every
`setup-env.sh` run, so the two cannot drift. Setting `ENV=dev` is the only
change needed to point the whole stack at a dev environment.

## Root cause of the empty 200 — Caddy was listening on :443

`https://whoami.maxrommel.de` returned HTTP 200 with an empty body for hours.
Everything looked correct: tunnel healthy, DNS right, Caddy healthy, routes
generated. Debug logging on cloudflared settled it:

```
DBG GET https://direct.maxrommel.de/TRACE21621 ... originService=http://caddy:80
DBG 200 OK content-length=0 ingressRule=0
```

Requests *were* reaching Caddy, and Caddy *was* answering 200 — with nothing in
it. `caddy adapt` showed why:

```
srv0: listen [":443"]  -> host whoami.maxrommel.de -> prod-whoami:8000
srv1: listen [":80"]   -> only /healthz
```

**A bare site address (`host.example.com {`) makes Caddy listen on :443, even
with `auto_https off`.** The port is inferred from the address, not from the
TLS setting. The tunnel connects to `caddy:80`, so every request fell through
to the `:80` healthz block and returned an empty 200.

Fix: the generator now emits `http://` on every site address. The template
carries a comment marking the prefix as load-bearing.

Second fix from the same investigation: the `:80` block now ends in an explicit
`404`. Because the tunnel rule is a wildcard, every subdomain reaches Caddy —
unregistered ones previously returned an empty 200 that looked like success and
would have hidden typos.

### Diagnostic lesson

Four layers each reported healthy while the path was broken. What resolved it
was following the request with debug logging rather than inspecting
configuration, and then asking Caddy what it had actually loaded (`caddy adapt`)
rather than reading what it was given. Effective config beats intended config.

## Two workarounds discovered

**Dashboard-managed tunnels ignore local `config.yml`.** A token-run tunnel
takes ingress from the Cloudflare dashboard. The generated
`compose/generated/cloudflared/config.yml` is therefore currently unused.

Mitigation: the dashboard holds exactly one static wildcard rule
(`*.maxrommel.de` → `http://caddy:80`), and Caddy — driven by `services.yml` —
does all real routing. One dashboard entry, set once, never touched again as
services are added. Migration to a locally-managed tunnel (credentials file +
`config.yml`) is tracked for M7, when SOPS makes storing those credentials safe.

**A wildcard `A` record cannot serve a tunnel.** The original
`A * → <host-ip>` pointed at the origin IP, which has no listener on 443 by
design — producing 522. Tunnel routing requires a `CNAME` to
`<tunnel-id>.cfargotunnel.com`, which Cloudflare represents as record type
`Tunnel`. Now corrected.

## Rollback

```bash
ssh -i ~/.ssh/life-server deploy@<host-ip> \
  'cd /opt/life-server && docker compose -f compose/docker-compose.prod.yml down'
```
Removes containers and networks; volumes survive. To remove those too, add `-v`.
Nothing in M1 is affected.
